# Migrating to 3.9.0

This guide covers the observable changes between 3.8.0 and 3.9.0. If you upgrade from an older version, also review the CHANGELOG between your version and 3.8.0 and the earlier migration guides, newest first: [3.8.0](3.8.0.md), [3.6.0](3.6.0.md). Each note describes one situation: whether you are affected, how it shows, and what to do.

## XDR definitions 579a90b

- If you `switch` over `XdrSCAddressType`, `XdrContractCostType` or the `Address.type` constants: in 3.9.0 address type 5 decodes to `SC_ADDRESS_TYPE_MUXED_CONTRACT`, cost types 86 to 94 decode to `MlDsa44DecodeVerifyingKey` through `VerifyMlDsa87Sig`, and `addressFromId` returns an `Address` of type `Address.TYPE_MUXED_CONTRACT` for a `W...` strkey. These types are classes of constants, so a `switch` statement without a `default` clause runs no case for the new values, and the analyzer reports nothing. In 3.8.0 decoding these values threw `Exception` with `Unknown enum value: <value>`, and `addressFromId` returned null for a `W...` strkey. Add cases for the new members or a `default` clause.

## Soroban authorization with muxed addresses

- If you match the message of `SorobanAuthorizationEntry.sign` for an `M...` `forAddress` target, or of `SorobanAuthorizationEntry.withDelegates` for an `M...` delegate: in 3.9.0 the texts name both muxed kinds, `Muxed account (M...) and muxed contract (W...) addresses are not valid Soroban auth targets; use the underlying G... or C... address instead` and `Muxed account (M...) and muxed contract (W...) addresses are not valid Soroban delegate addresses: <address>`. A `W...` address fails the same way. In 3.8.0 the texts began `Muxed addresses (M...) are not valid Soroban`, and the target text ended `use the underlying G... account address instead`. Update the patterns. `sign` throws `Exception`; `withDelegates` throws `ArgumentError`, which escapes `on Exception catch`.
- If you sign with `SorobanAuthorizationEntry.sign` an entry whose credential address is a muxed account (`M...`) or muxed contract (`W...`): in 3.9.0 the call throws `Exception` with `Muxed account (M...) and muxed contract (W...) addresses are not valid Soroban auth credential addresses: <address>; use the underlying G... or C... address instead`, and the entry stays unsigned. In 3.8.0 an entry with an `M...` credential came back signed, and the host rejected it. Build the entry for the address behind the muxed one, `MuxedAccount.fromMed25519AccountId(address).ed25519AccountId` or `MuxedContract.fromMuxedContractId(address).contractId`.

## Asset codes in XDR-JSON

- If you decode hand-written or third-party XDR-JSON with a twelve-byte asset code that unescapes to fewer than five bytes, four-character codes included: in 3.9.0 `fromXdrJson` throws `FormatException` with `XDR-JSON XdrAssetAlphaNum12 key "asset_code" holds 3 bytes, fewer than the minimum of 5; a shorter code is written with escaped NUL padding` for `"ABC"`. This covers the `asset_code` of `XdrAssetAlphaNum12`, as in a `credit_alphanum12` asset, and every other `AssetCode12` field. In 3.8.0 such a string decoded to an asset code that the network rejects as invalid. Write the code with escaped NUL bytes up to five bytes, in the JSON document as `"ABC\\0\\0"`. XDR-JSON that the SDK writes already has this form, and `XdrAssetAlphaNum4` is unaffected.

## Contract address parameters

- If you pass an address string to `ContractSpec.nativeToXdrSCVal` or `ContractSpec.funcArgsToXdrSCValues` and catch the error for a malformed `G...` or `C...` strkey: in 3.9.0 the conversion throws `ContractSpecException` with `Invalid type: Invalid address format: <value>; Address takes an account (G...) or contract (C...) address` for an `Address` parameter. In 3.8.0 a malformed `G...` or `C...` string threw the strkey decoder's `FormatException`, for example `FormatException: Checksum invalid`. Catch `ContractSpecException`, or catch `Exception`, which covers both versions.
- If you convert a 64-character hex contract id or an `Address` to a strkey before passing it to `ContractSpec.nativeToXdrSCVal` or `ContractSpec.funcArgsToXdrSCValues`: in 3.9.0 the conversion takes the hex as that contract's address and converts an `Address` of type account or contract directly. In 3.8.0 a hex id threw `ContractSpecException` with `Invalid type: Invalid address format: <value>` unless it began with an uppercase `C`, and an `Address` threw `Invalid type: Expected String address, got Address`. Keep the conversion or pass the value as it is; both produce the same argument.
- If you build the `XdrSCVal` yourself for a `MuxedAddress` parameter of `ContractSpec.nativeToXdrSCVal` or `ContractSpec.funcArgsToXdrSCValues`: in 3.9.0 the conversion takes an `M...` or `W...` strkey, or an `Address` of type muxed account or muxed contract, directly, and a prebuilt `XdrSCVal` still passes through unchanged. In 3.8.0 a strkey or an `Address` for that parameter threw `ContractSpecException` with `Invalid type: Unsupported value type: SCSpecType.20`. Keep the prebuilt value or pass the address directly; both produce the same argument.
- If you match the messages of `ContractSpecException` for address arguments: in 3.9.0 a claimable balance (`B...`) address gives `Invalid type: <expected>, got the claimable balance address <address>, which is produced by the host and is not a contract input`, and a liquidity pool (`L...`) address the same text with `liquidity pool address`. A muxed address for an `Address` parameter gives `Invalid type: <expected>, got the muxed address <address>, which needs a MuxedAddress parameter`, and another type `Invalid type: <expected>, got <type>`. `<expected>` names the kinds the parameter takes. In 3.8.0 these strings gave `Invalid type: Invalid address format: <value>`, and other types `Invalid type: Expected String address, got <type>`. Update the patterns; the exception type is unchanged.

## XDR definitions c2612cf

- If you `switch` over `XdrStellarValueType` or read the arms of `XdrStellarValueExt`, for example in `XdrLedgerHeader.scpValue.ext`: in 3.9.0 the type decodes `STELLAR_VALUE_SIGNED_MS` (3) and `STELLAR_VALUE_EMPTY_TX_SET_MS` (4), whose arms are `signedMsValue` (`closeTimeMs`, `lcValueSignature`) and `proposedMsValue`. A `switch` statement without a `default` clause runs no case for them, and `ext.lcValueSignature` is null for type 3. In 3.8.0 decoding either type threw `Exception` with `Unknown enum value: <value>`. Add cases that read `signedMsValue` and `proposedMsValue`, or a `default` clause. `closeTimeMs` is the ledger close time in milliseconds.

## Signing assembled transactions

- If you pass `validUntilLedgerSeq` to `AssembledTransaction.signAuthEntries` for an auth entry that already carries a signature, such as a `SOROBAN_CREDENTIALS_ADDRESS_WITH_DELEGATES` entry another signer has signed: in 3.9.0 a value other than the entry's stored `signatureExpirationLedger` throws `ArgumentError`, for example `Invalid argument (validUntilLedgerSeq): Auth entry 0 already carries a signature committed to signatureExpirationLedger 4000: 4010`. In 3.8.0 every call wrote its expiration into the entry, which invalidated the signatures already on it, and the host rejected the transaction. Omit the value on later calls, which keeps the stored expiration, or pass the stored value. `ArgumentError` escapes `on Exception catch`.

  ```dart
  // 3.8.0
  await tx.signAuthEntries(signerKeyPair: owner, validUntilLedgerSeq: ownerExpiration);
  await tx.signAuthEntries(signerKeyPair: delegate, validUntilLedgerSeq: delegateExpiration);
  ```

  ```dart
  // 3.9.0
  await tx.signAuthEntries(signerKeyPair: owner, validUntilLedgerSeq: ownerExpiration);
  await tx.signAuthEntries(signerKeyPair: delegate);
  ```

- If you catch a failure of `AssembledTransaction.signAuthEntries`, for example from your `authorizeEntryDelegate`, and go on with the transaction: in 3.9.0 the call signs copies and replaces the transaction's auth entries only after every matching entry is signed, so a call that throws leaves them as they were. In 3.8.0 the entries signed before the failure kept their new signatures and expiration. Call `signAuthEntries` again after you fix the cause.
- If you call `AssembledTransaction.sign` or `signAndSend` while the top-level account (`G...`) of an auth entry is unsigned: in 3.9.0 the call throws `Exception` with ``Transaction requires signatures from multiple signers. See `needsNonInvokerSigningBy` for details.`` before anything is submitted. This holds for a `SOROBAN_CREDENTIALS_ADDRESS_WITH_DELEGATES` entry whatever its delegate nodes carry, and a void or empty-vector signature counts as unsigned. In 3.8.0 the call went ahead when every delegate node was signed or the delegate list was empty, and the host rejected the transaction; it also took an empty-vector signature as signed. Sign that account's entry with `signAuthEntries` first; `needsNonInvokerSigningBy` lists it. An unsigned contract (`C...`) blocks at neither level; in 3.8.0 an unsigned contract delegate stopped the call.

## Map key order

- If you pass a `Map`, a map-encoded struct, or a `Map` for an `SC_SPEC_TYPE_VAL` value to `ContractSpec.nativeToXdrSCVal` or `ContractSpec.funcArgsToXdrSCValues`: in 3.9.0 the resulting `SCV_MAP` holds its keys in the Soroban host's order, the order of `compareScValHostOrder`, whatever the insertion order. In 3.8.0 the map kept its insertion order, and the host rejected a call whose keys were out of its order. Calls need no change. A sort you added before the conversion can go, and a test that compares the encoded XDR with an insertion-ordered map needs the sorted order. Decoded XDR keeps its map order.
- If two keys of such a map are equal in host order, for example two `Uint8List` keys with the same bytes: in 3.9.0 the conversion throws `ArgumentError` with `Invalid argument (entries): Duplicate ScMap key: <key>`, where `<key>` is the key's XDR-JSON in quotes. In 3.8.0 both entries were encoded, and the host rejected the map. Remove the duplicate key. `ArgumentError` escapes `on Exception catch`.

## Asset order in liquidity pools

- If you build an `AssetTypePoolShare` from two credit assets of the same type and code with different issuers: in 3.9.0 the issuers compare by their raw 32-byte public keys, as stellar-core does, and the constructor throws `Exception` for the reversed pair. In 3.8.0 the SDK compared the issuers' `G...` text, so for some pairs it accepted the order stellar-core rejects and threw for the order stellar-core uses. The two orders differ when, at the first character where the issuers differ, one holds a digit from 2 to 7 and the other a letter. Pass such a pair in the other order. The issuers below first differ at `2` and `H`.

  ```dart
  // 3.8.0
  final usd2 = AssetTypeCreditAlphaNum4('USD', 'GD2VSLB7BPYNKQIF2P632VIVMVXPMU2B5RJU2WO4GATAJRSIDC24ZDUO');
  final usdH = AssetTypeCreditAlphaNum4('USD', 'GDHXVH2CWS5EZLHKSHQXPLVWVJUNNXGLA2RBQQFS3LMMQIXD437QEIRQ');
  final poolShare = AssetTypePoolShare(assetA: usd2, assetB: usdH);
  ```

  ```dart
  // 3.9.0
  final usd2 = AssetTypeCreditAlphaNum4('USD', 'GD2VSLB7BPYNKQIF2P632VIVMVXPMU2B5RJU2WO4GATAJRSIDC24ZDUO');
  final usdH = AssetTypeCreditAlphaNum4('USD', 'GDHXVH2CWS5EZLHKSHQXPLVWVJUNNXGLA2RBQQFS3LMMQIXD437QEIRQ');
  final poolShare = AssetTypePoolShare(assetA: usdH, assetB: usd2);
  ```

- If you decode pool share change-trust XDR with `Asset.fromXdrChangeTrustAsset`, for example from a transaction on the network: in 3.9.0 a pool of two same-code assets decodes in the order stellar-core uses. In 3.8.0 such a pool threw the wrong-order `Exception` when, at the first character where its issuers differ, one holds a digit and the other a letter. Remove any workaround for that failure.
- If you match the message that the `AssetTypePoolShare` constructor or `Asset.fromXdrChangeTrustAsset` throws for a reversed pair: in 3.9.0 it reads `Assets are in wrong order: assetA <assetA> sorts after assetB <assetB>. Sort by: Native < AlphaNum4 < AlphaNum12, then by Code, then by the Issuer's raw public key bytes.`, where `<assetA>` and `<assetB>` read `CODE:ISSUER`. In 3.8.0 it read `Assets are in wrong order. Sort by: Native < AlphaNum4 < AlphaNum12, then by Code, then by Issuer, using lexicographic ordering.` Update the patterns.

## Diagnostic events of getTransaction

- If you read the diagnostic events of `SorobanServer.getTransaction` through `GetTransactionResponse.events?.diagnosticEventsXdr`, or decode them from the transaction meta yourself: in 3.9.0 `GetTransactionResponse.diagnosticEventsXdr` holds the list that stellar-rpc sends at the top level of the result; decode an entry with `XdrDiagnosticEvent.fromBase64EncodedXdrString`. In 3.8.0 the response had no top-level list, and `events?.diagnosticEventsXdr` stayed null because stellar-rpc does not send that field. Read the top-level list and drop the workaround. The nested property is deprecated and still decodes the field in older response data.
