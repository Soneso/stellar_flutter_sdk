# Migrating to 3.6.0

This guide covers the observable changes between 3.5.0 and 3.6.0. If you upgrade from an older version, also review the CHANGELOG entries between your version and 3.5.0. Each note describes one situation: whether you are affected, how it shows, and what to do.

- If you build Soroban authorization entries or read them from simulation: `SorobanCredentials.forAddress()` / `forAddressCredentials()` build `ADDRESS_V2` under unchanged signatures. In 3.5.0 these factories built `ADDRESS`. To keep that arm, use `forAddressLegacy()` / `forAddressCredentialsLegacy()` and pass `useUpgradedAuth: false` to simulation. This is needed on networks below Protocol 27 and with services that reject V2 credentials. Code reading `SorobanCredentials.addressCredentials` from V2 simulation results gets null, so null-aware writes silently do nothing. Read and write through `innerAddressCredentials`.
- If your OpenZeppelin smart account relayer cannot parse Protocol 27 authorization XDR: submissions fail. In 3.5.0 the default credentials were legacy `ADDRESS`. Set `useUpgradedAuth: false` in `OZSmartAccountConfig`. If an external wallet cannot sign the address-bound preimage, set `useUpgradedAuthForWalletSigners: false`. Direct callers of `OZSmartAccountAuth.buildSourceAccountAuthPayloadHash` get a compile error. Pass the credential address, and pass `useUpgradedAuth: false` when building legacy credentials, so the hash matches the credential arm.
- If you use CAP-85 tags as text: `XdrContractExecutableExternalRef.tag`, its constructor's tag parameter, and `XdrSCVal.executableTag` are `Uint8List`/`Uint8List?`. A `String` use fails to compile; a `var` or `dynamic` use receives bytes. In 3.5.0 these values were strings. Read text through `tagString` / `executableTagString`; non-text bytes throw `FormatException`. The text factories `XdrSCVal.forExecutableTag(String)` and `XdrContractExecutable.forExternalRef(XdrSCAddress, String)` are unchanged. To build from bytes, use `XdrSCVal.forExecutableTagBytes` / `XdrContractExecutable.forExternalRefBytes` or the positional constructor.
- If you decode strkeys from user input or storage: malformed input throws `FormatException`. In 3.5.0 some malformed input decoded or failed with `RangeError`. Catch `FormatException` around decode calls, or validate first with `StrKey.isValid*`.
- If you build keypairs from raw bytes: `KeyPair.fromPublicKey` and `fromSecretSeedList` throw `ArgumentError` for key material that is not 32 bytes. In 3.5.0 `fromPublicKey` accepted a mis-sized key and `fromSecretSeedList` threw an `Exception`. `ArgumentError` is an `Error`, so `on Exception catch` does not catch it. Catch it explicitly or check the byte length first.
- If you pass an M-address to `SignedPayloadSigner.fromAccountId`: it throws `ArgumentError`, which requires an explicit catch. In 3.5.0 the signer named the base account's key. To sign for that account, convert the address with `MuxedAccount.fromMed25519AccountId(m).ed25519AccountId` and pass the G-address.
- If you call `Util.stringIdToXdrHash`: the removed method causes a compile error. Rename calls with a 64-character hex ID to `Util.hexIdToXdrHash(hexId, idKind)`. The `idKind` argument names the ID in error messages. Use `Util.liquidityPoolIdToXdrHash(id)` for a pool ID in L-address or hex form. Wrong-width input throws. In 3.5.0 wrong-width input was padded or truncated into a hash.
- If you store or compare claimable balance IDs: parsed XDR returns 72-character hex IDs through `ClaimClaimableBalanceOperation.balanceId`, `ClawbackClaimableBalanceOperation.balanceId`, and `Address.fromXdr`. In 3.5.0 the operations returned 64 characters and the address helper returned 66. Stored-string comparisons can fail. Convert both sides with `RequestBuilder.claimableBalanceIdHorizonHex()` before comparing, or store the 72-character form. Input APIs accept every spelling. `SubmitTransactionResponse.getClaimableBalanceIdIdFromResult` returns the 64-character form.
- If your app stored a 63-character B-address: it is not a valid SEP-23 strkey, and decoding fails. In 3.5.0 `StrKey.encodeClaimableBalanceId` could build that form from the ID's 36-byte XDR encoding. Fetch the balance's ID through `sdk.claimableBalances.forClaimant(...)` and store what Horizon returns. A valid B-address has 58 characters.
- If you pass price strings to offer builders or `LiquidityPoolDepositOperationBuilder`: zero and prices without a signed-int32 fraction throw during XDR conversion. This happens at signing or envelope rendering. In 3.5.0 these prices produced transactions the network rejected as malformed. Validate with `Price.fromString(input)` in a try/catch where the price enters your app, or handle the exception at signing. This applies to `ManageSellOfferOperationBuilder`, `ManageBuyOfferOperationBuilder`, `CreatePassiveSellOfferOperationBuilder`, and deposit `minPrice`/`maxPrice`. Offer deletion with amount `"0"` and a valid price is unaffected.
- If you accept amount or price strings from users: malformed text throws from `Util.decimalStringToStroops` and `Price.fromString`. In 3.5.0 malformed text could parse into an incorrect value that reached the network. Keep the exception if it suits your flow, or validate input where you want a friendly error message.
- If you pass IDs, encode strkeys, or parse TxRep: wrong lengths or discriminants throw at the call. In 3.5.0 these inputs could return incorrect values. Validate IDs at input or handle the exception. This affects `XdrClaimableBalanceID.forId` and its operations and helpers, contract and liquidity pool helpers, TxRep parsers, and `StrKey` encoders. Hex contract and pool IDs require 64 characters. Existing `on Exception catch` handlers cover these rejections except for `LiquidityPoolDepositOperation` and `LiquidityPoolWithdrawOperation`: their `ArgumentError` requires an explicit catch.
