# Migrating to 3.6.0

This guide covers the observable changes between 3.5.0 and 3.6.0. If you upgrade from an older version, also review the CHANGELOG entries between your version and 3.5.0. Each note describes one situation: whether you are affected, how it shows, and what to do.

- If you build Soroban authorization entries or read them from simulation: `SorobanCredentials.forAddress()` / `forAddressCredentials()` now build `ADDRESS_V2` under unchanged signatures — existing calls change arm without a compile error. To keep the legacy `ADDRESS` arm, use `forAddressLegacy()` / `forAddressCredentialsLegacy()` and pass `useUpgradedAuth: false` to simulation (needed on networks below Protocol 27 and with services that reject V2 credentials). Code reading `SorobanCredentials.addressCredentials` off simulation results gets null under V2, so null-aware writes silently do nothing; read and write through `innerAddressCredentials` instead.
- OpenZeppelin smart accounts: if your relayer rejects submissions after the upgrade (it cannot parse Protocol 27 authorization XDR), set `useUpgradedAuth: false` in `OZSmartAccountConfig`; if an external wallet can no longer sign (it cannot sign the address-bound preimage type), set `useUpgradedAuthForWalletSigners: false`. Direct callers of `OZSmartAccountAuth.buildSourceAccountAuthPayloadHash` get a compile error: pass the address the new credentials will carry, and `useUpgradedAuth: false` when building legacy credentials, so the hash matches the credential arm.
- Code using the 3.5.0 CAP-85 types gets a compile error wherever the tag value is used as a `String` (`XdrContractExecutableExternalRef.tag`, its positional constructor's tag parameter, and `XdrSCVal.executableTag` are now `Uint8List`/`Uint8List?`); a `var` or `dynamic` use compiles and silently becomes bytes. Read text tags through `tagString` / `executableTagString` (a `FormatException` means the bytes spell no text). The text factories `XdrSCVal.forExecutableTag(String)` and `XdrContractExecutable.forExternalRef(XdrSCAddress, String)` are unchanged; to build from bytes, use `XdrSCVal.forExecutableTagBytes` / `XdrContractExecutable.forExternalRefBytes` or the positional constructor.
- If you decode strkeys from user input or storage: malformed input that previously decoded, or failed with a `RangeError`, now throws a `FormatException`. Catch `FormatException` around decode calls — `RangeError` handlers no longer fire — or validate first with `StrKey.isValid*`.
- If you build keypairs from raw bytes: `KeyPair.fromPublicKey` and `fromSecretSeedList` throw `ArgumentError` for key material that is not 32 bytes. `ArgumentError` is an `Error`, so `on Exception catch` does not catch it — catch it explicitly or check the byte length first.
- If you passed an M-address to `SignedPayloadSigner.fromAccountId`: it now throws `ArgumentError` (same catch caveat). The signer you built always named the base account's key — if that is the intent, convert it yourself (`MuxedAccount.fromMed25519AccountId(m).ed25519AccountId`) and pass the G-address.
- If you called `Util.stringIdToXdrHash`: it is removed (compile error). For a correctly sized 64-character hex id, renaming to `Util.hexIdToXdrHash(hexId, idKind)` is enough (`idKind` names the id in the error message); use `Util.liquidityPoolIdToXdrHash(id)` for a pool id in the `L...` or hex spelling. Wrong-width input, which was previously padded or truncated into a hash for an id you never passed, now throws.
- If you store or compare claimable balance ids: ids read back from parsed XDR are spelled longer now. `ClaimClaimableBalanceOperation.balanceId` and `ClawbackClaimableBalanceOperation.balanceId` return the 72-character hex Horizon uses (previously 64 characters), and `Address.fromXdr` the same (previously 66), so comparisons against ids stored before 3.6.0 fail on the spelling. Convert both sides with `RequestBuilder.claimableBalanceIdHorizonHex()` before comparing, or store the new form. Nothing you pass into the SDK needs converting — the balance-id APIs accept every spelling — and `SubmitTransactionResponse.getClaimableBalanceIdIdFromResult` intentionally still returns the 64-character form.
- If your app stored a `B...` id string that is 63 characters long instead of the correct 58 — possible only if it was built with 3.5.0's `StrKey.encodeClaimableBalanceId` from the id's 36-byte XDR encoding — those strings are not valid SEP-23 strkeys, and 3.6.0 no longer decodes them. Re-fetch the balance's id (e.g. `sdk.claimableBalances.forClaimant(...)`) and store what Horizon returns.
- If you pass a price string to `ManageSellOfferOperationBuilder`, `ManageBuyOfferOperationBuilder`, `CreatePassiveSellOfferOperationBuilder`, or `LiquidityPoolDepositOperationBuilder` (`minPrice`/`maxPrice`): a price of `"0"`, or one no signed-int32 fraction can represent, now throws when the operation is converted to XDR — that is, at `transaction.sign(...)` or when rendering the envelope — where it previously produced a transaction the network rejected as malformed. Offer deletion (amount `"0"` with a valid price) is unaffected. To validate early, run `Price.fromString(input)` in a try/catch where the price enters your app — it applies exactly the checks serialization applies later — and show your own error message on the exception; otherwise handle the exception at signing.
- If you accept amount or price strings from users: malformed text previously parsed into a wrong-but-valid value and could reach the network (examples in the body above); `Util.decimalStringToStroops` and `Price.fromString` now throw instead. Nothing to change if an exception is acceptable there; pre-validate where you want a friendly error message.
- If your app passes claimable balance ids, contract ids, or liquidity pool ids (hex or strkey), encodes strkeys from raw bytes, or parses TxRep text: a value of the wrong length, or with a wrong discriminant, previously produced a wrong-but-usable result and now throws at the call. The affected APIs are `XdrClaimableBalanceID.forId` and everything built on it (the claim, clawback, and revoke-sponsorship operations; the address, ledger-key, and SCVal helpers), the contract and liquidity pool helpers (a hex id must be exactly 64 characters / 32 bytes), the TxRep parsers, and the `StrKey` encoders. An existing `on Exception catch` around these calls picks the new rejections up automatically — except for `LiquidityPoolDepositOperation` and `LiquidityPoolWithdrawOperation`, whose `ArgumentError` is an `Error` and escapes it. Calls with no catch now propagate exceptions where they previously returned a value: validate these ids where they enter your app, or add handling at the call.
