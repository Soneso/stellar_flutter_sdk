# Migrating to 3.8.0

This guide covers the observable changes between 3.7.0 and 3.8.0. If you upgrade from an older version, also review the CHANGELOG entries between your version and 3.7.0 and the [3.6.0 migration notes](3.6.0.md). Each note describes one situation: whether you are affected, how it shows, and what to do.

## SEP-29 memo-required check on submission

- If you submit transactions through `StellarSDK.submitTransaction`, `submitFeeBumpTransaction`, `submitAsyncTransaction`, `submitAsyncFeeBumpTransaction`, `submitTransactionEnvelopeXdrBase64` or `submitAsyncTransactionEnvelopeXdrBase64`: a transaction without a memo (memo `null` or `MemoNone`) that pays into, path-pays into or merges into a `G...` account whose `config.memo_required` data entry is `1` now throws `AccountRequiresMemoException` and nothing is submitted. In 3.7.0 the SDK attempted submission without checking memo requirements. The exception carries `accountId` and `operationIndex` (zero-based over all operations of the transaction) and prints as `Destination account <accountId> of operation <operationIndex> requires a memo in the transaction.`. Catch it with `on AccountRequiresMemoException catch (e)` and rebuild the transaction with a memo, or pass `skipMemoRequiredCheck: true` to submit without the check. Multiplexed (`M...`) destinations are not looked up, and a destination Horizon does not know (404) is skipped. Fee bump transactions are checked through their inner transaction.
- If you submit memo-less transactions with payment, path payment or account merge operations: each submit call now sends `GET /accounts/<id>` to Horizon for every distinct non-muxed destination, in operation order, before it posts the transaction. It stops at the first account that requires a memo. This adds latency and counts against Horizon rate limits; a transaction that carries a memo triggers no lookup. A lookup that fails with anything other than 404 stops the submit call before anything is posted: `ErrorResponse` for another HTTP status, `TooManyRequestsException` for a rate limit, `http.ClientException` for a transport failure. In 3.7.0 these methods posted directly without destination-account lookups; in 3.8.0 a lookup error can stop the call before the transaction is posted. To keep the submit call to one request, run `StellarSDK.checkMemoRequired(transaction)` earlier, for example before a confirmation screen, and submit with `skipMemoRequiredCheck: true`.
- If you submit with a mocked or restricted HTTP client: the destination lookups go through the same `http.Client` as the submission. A mock that throws for `GET /accounts/<id>`, returns an error status other than 404, or returns an invalid account response can now stop the submit call; a proxy allow-list must also permit the accounts endpoint. Return a valid account response from the mock, return 404 to skip that destination, or pass `skipMemoRequiredCheck: true` in tests that only exercise submission.
- If you use SEP-7 `URIScheme.signAndSubmitTransaction()`: when the URI has no callback URL, the method submits directly to the network and now runs the check, so it can throw `AccountRequiresMemoException` and the lookup errors above. It has no `skipMemoRequiredCheck` parameter. The callback-URL path is unchanged. Catch the exception where you call it; to submit without the check, read the `xdr` parameter with `URIScheme.tryParseSep7Url`, decode it with `AbstractTransaction.fromEnvelopeXdrString`, sign it, and call `StellarSDK.submitTransaction` (or `submitFeeBumpTransaction`) with `skipMemoRequiredCheck: true`.
- If you subclass `StellarSDK` and override one of the six submit methods: the override no longer compiles, because the overridden method now declares the named parameter `{bool skipMemoRequiredCheck = false}`. Add the parameter to your override and forward it. If a class of yours `implements StellarSDK`, it must also implement `Future<void> checkMemoRequired(AbstractTransaction transaction)`.

## Stricter XDR decoding

- If you decode XDR from sources you do not control, or XDR produced by a newer protocol than the SDK knows: a union discriminant that has no arm now throws `Exception("Unknown <Type> discriminant: <value>")`, for example `Exception: Unknown XdrTransactionExt discriminant: 2`. In 3.7.0 the decoder returned a partially populated object and read the following bytes as the next field. This covers every union with an `int` discriminant (the `...Ext` unions, `XdrTransactionMeta`, `XdrLedgerCloseMeta`, `XdrTransactionPhase`, `XdrGeneralizedTransactionSet` and others) and the enum-discriminated `XdrAsset`, `XdrAllowTrustOpAsset`, `XdrMuxedAccount`, `XdrTransactionEnvelope`, `XdrFeeBumpTransactionInnerTx`, `XdrInnerTransactionResultResult`, `XdrHashIDPreimage` and `XdrTransactionSignaturePayloadTaggedTransaction`. The type is a plain `Exception`, so an existing `on Exception catch` around the decode picks it up. Code that inspected the partial object must treat such input as undecodable.
- If you decode malformed or truncated XDR: `XdrDataInputStream` and `DataInput` now throw `RangeError` with new messages before reading past the input. An array count is checked against the remaining bytes before any element is decoded (`XDR array count cannot be negative, got -1`, `XDR array count 5 exceeds the maximum of 2 for the 8 remaining bytes`), a `string` or `opaque` length likewise (`XDR byte count cannot be negative, got -1`, `XDR byte count 9 exceeds the 8 remaining bytes`), and a fixed-width read that runs past the input reports `XDR read of 4 bytes exceeds the 0 remaining bytes`. In 3.7.0 a negative array count decoded as an empty list in the generated decoders, and a truncated input surfaced as `RangeError("Reached end of file")` or as the platform's own out-of-bounds error. `RangeError` is an `Error`, so `on Exception catch` does not catch it; catch `RangeError` or `Error` explicitly. Code that matches the text `Reached end of file` must match the new messages.
- If you call `WebAuthForContracts.decodeAuthorizationEntries` (SEP-45): a negative or over-long entry count now throws `ContractChallengeValidationException` whose message ends with the `RangeError` text above, for example `Failed to decode authorization entries: RangeError: XDR array count cannot be negative, got -1`. In 3.7.0 a negative count returned an empty entry list.
- If you validate SEP-7 URIs with `URIScheme.isValidSep7Url`: an `xdr` parameter with an unhandled union arm is reported as invalid (`result: false`, reason `The provided 'xdr' parameter is not a valid transaction envelope`). In 3.7.0 some such inputs passed, for example an otherwise valid envelope whose `XdrTransactionExt` discriminant was 2; others were already rejected during conversion to SDK objects. An envelope with a negative array count now throws `RangeError` out of `isValidSep7Url`, because the method catches `Exception` only; in 3.7.0 it returned `false` for a negative operations count and `true` for a negative count in another array. An over-long count already escaped in 3.7.0, as `RangeError("Reached end of file")` or the platform's own out-of-bounds error, and now escapes with the array count message. If such input can reach the call, wrap it in `on Error catch`.
- If you pass a `Uint8List` that is a view on a larger buffer (a nonzero `offsetInBytes`, for example from `Uint8List.sublistView`) to `XdrDataInputStream` or `DataInput.fromUint8List`: integer and floating-point reads now decode the view's own bytes. In 3.7.0 they read from the start of the underlying buffer, so such input decoded wrong values. Code that copied the view into a fresh `Uint8List` first still works and can drop the copy.

## Prices

- If you store or compare the `price` string of a `ManageBuyOfferOperation`, `ManageSellOfferOperation` or `CreatePassiveSellOfferOperation` built from XDR through `builder(...)`, or the `minPrice` and `maxPrice` of a `LiquidityPoolDepositOperation` built the same way: the string is now the exact decimal expansion of the XDR fraction, truncated after 20 fraction digits and never in exponent notation. In 3.7.0 it was a `double` rendering: 1/10000000 read `"1e-7"` and 1/3 read `"0.3333333333333333"`; in 3.8.0 they read `"0.0000001"` and `"0.33333333333333333333"`. Re-encoding an operation whose price rendered in exponent notation threw `Exception("Not a decimal price: 1e-7")` in 3.7.0 and now succeeds. Strings stored by an app built with 3.7.0 can differ from what 3.8.0 renders for the same operation. Where you retain the original XDR or its price numerator and denominator, regenerate the display string from those values and compare the underlying fractions. `Price.fromString` cannot parse legacy exponent strings such as `"1e-7"`; if only a rounded legacy display string remains, do not assume it identifies the original fraction exactly.
- If you call `Price.fromString`: it now reads the decimal exactly and returns the exact fraction whenever one fits int32. Some inputs yield a different `n/d` than in 3.7.0: `"0.000000004096"` is 1/244140625 (3.7.0: 1/244140627) and `"0.99999999"` is 99999999/100000000 (3.7.0: 1799999971/1799999989). At the int32 boundaries the result follows the exact value: a decimal just above 1/2147483648 parses to 1/2147483647, and a value below -2147483648 whose excess only showed beyond `double` precision is now refused with `Exception("Not a price an int32 fraction can carry: ...")`. The accepted syntax and both exception messages are unchanged. Tests that pin the 3.7.0 fractions need the exact values.
- If you decode operation XDR with a zero price denominator: the `builder(...)` methods for `ManageBuyOfferOperation`, `ManageSellOfferOperation`, `CreatePassiveSellOfferOperation` and `LiquidityPoolDepositOperation` now throw `ArgumentError` while rendering the price. In 3.7.0 they produced `"Infinity"`, `"-Infinity"` or `"NaN"` instead. This also affects `Operation.fromXdr`, transaction-envelope parsing and `URIScheme.isValidSep7Url`. Catch `ArgumentError` and reject the malformed input; it is an `Error`, so `on Exception catch` does not catch it. Calling `Price.toDecimalString()` directly with a zero denominator throws the same error.
- If you call `removeTailZero` with a string that has no decimal point: it now returns the string unchanged. In 3.7.0 `removeTailZero("100")` returned `"1"`.

## Liquidity pool ids in Horizon request builders

- If you pass a liquidity pool id to `AccountsRequestBuilder.forLiquidityPool`, `EffectsRequestBuilder.forLiquidityPool`, `LiquidityPoolsRequestBuilder.forPoolId`, `LiquidityPoolTradesRequestBuilder.forPoolId`, `OperationsRequestBuilder.forLiquidityPool`, `TradesRequestBuilder.liquidityPoolId` or `TransactionsRequestBuilder.forLiquidityPool`: a hex id must now be exactly 64 hex characters, and it is sent to Horizon in lowercase. Any other string that does not start with `L` throws `ArgumentError("invalid liquidity pool id: <id> (<reason>)")` before a request is made, for example `invalid liquidity pool id: abc123 (Liquidity pool id must be hex of a 32 byte hash; 3 bytes given)`. In 3.7.0 such a string was sent to Horizon as given. `ArgumentError` is an `Error`; catch it explicitly, or validate the id where it enters your app with `RequestBuilder.liquidityPoolIdHorizonHex(id)`, which applies the same check.
- If you match the message of the `ArgumentError` thrown for a malformed `L...` id: it now ends with the decoder's reason in parentheses, for example `invalid liquidity pool id: L... (Checksum invalid)`, where 3.7.0 stopped after the id.

## Removed and retyped API

- If you read `Network.networkId`: it is declared `Uint8List` instead of `Uint8List?`; it never returned null. `networkId!` still compiles and the analyzer reports the `!` as an unnecessary non-null assertion; `networkId?.` gets an unnecessary null-aware warning. Remove the `!` and `?.`. A subclass overriding the getter, or a class implementing `Network`, no longer compiles while its getter returns `Uint8List?`; change the return type to `Uint8List`.
- If you reference `NetworkConstants.TRANSACTION_TIME_BUFFER_SECONDS`: it is removed and the reference fails to compile. The constant had the value 10, was deprecated since 3.5.0, and was unused by the SDK in 3.7.0. Delete the reference, or define the value in your own code.
- If a class of yours `implements Price`, `XdrDataInputStream` or `SorobanServer` (Dart implicit interfaces): it fails to compile with a missing concrete implementation, because these classes gained instance members. Add `String toDecimalString()` to a `Price` implementation, `int readArrayLength()` to an `XdrDataInputStream` implementation, and the getter and setter of `void Function(String message)? logger` to a `SorobanServer` implementation, unless the class uses `noSuchMethod`. Classes that `extend` these types, and ordinary callers, are unaffected.

## `SorobanServer` logging

- If you read `SorobanServer` output on the console: with `enableLogging = true` the `<method> response: <body>` lines, and the TLS warning printed when `httpOverrides` is enabled, no longer appear on stdout. In 3.7.0 both went through `print`. In 3.8.0 they go to the new `logger` field when set, and otherwise to `dart:developer` `log` under the name `stellar_flutter_sdk.SorobanServer` (`SorobanServer.logName`), which only developer tooling that receives `dart:developer` log records shows. To restore console output, pass `logger: print` to the `SorobanServer` constructor or set `server.logger = print`. `SorobanClient.forClientOptions` sets a newly constructed server's logging from `ClientOptions.enableServerLogging`. `AssembledTransaction.build` and `AssembledTransaction.buildWithOp` use `AssembledTransactionOptions.enableSorobanServerLogging` when they construct a server. Install and deploy requests use their `enableSorobanServerLogging` field. These SDK-created servers have no custom logger. To receive their messages, construct a `SorobanServer` with a `logger`, set its `enableLogging` field to `true`, and pass it as `ClientOptions.server` or the request's `server`. A provided server keeps its own `enableLogging` setting.

## External reference deployment

- If you match the message of the `Exception` thrown by `SorobanClient.deployFromExternalRef` for a `DeployFromExternalRefRequest` whose `executableOwner` is not a contract address: the message now reads `external reference owner <owner> is not a contract: the executable owner of an external reference must be a contract`. In 3.7.0 the same request failed with `external reference does not resolve: owner <owner> holds no 32-byte wasm hash entry under tag <tag>`, which in 3.8.0 covers only a contract owner whose reference does not resolve. With the SDK's default server, no RPC request is made for a non-contract owner in either version.
- If you pass a custom `SorobanServer` through `DeployFromExternalRefRequest.server` and override `getExternalRefWasmHash`: a non-contract `executableOwner` is now rejected before your override is called. In 3.7.0 the call reached that override. Move any validation or recording of these rejected attempts to the caller, and update mocks that expected a lookup for a non-contract owner.
