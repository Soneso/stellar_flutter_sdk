# Migrating to 3.13.0

This guide covers the observable changes between 3.12.0 and 3.13.0. If you upgrade from an older version, also review the CHANGELOG between your version and 3.12.0 and the earlier migration guides, newest first: [3.12.0](3.12.0.md), [3.9.0](3.9.0.md), [3.8.0](3.8.0.md), [3.6.0](3.6.0.md). Each note describes one situation: whether you are affected, how it shows, and what to do.

## Offer ids in XDR

- If your code uses an `XdrUint64` for the `offerID` of an `XdrManageSellOfferOp`, `XdrManageBuyOfferOp`, `XdrOfferEntry`, `XdrLedgerKeyOfferBase`, `XdrLedgerKeyOffer`, `XdrClaimOfferAtom`, or `XdrClaimOfferAtomV0`, in a read, a constructor argument, an assignment, or a typed variable: the code does not compile. The field is an `XdrInt64`. For a read, the analyzer reports `The getter 'uint64' isn't defined for the type 'XdrInt64'.` In 3.12.0 the field was an `XdrUint64`. Read the id with `.int64`, create the field with `XdrInt64(id)`, and declare offer id variables as `XdrInt64`. `ManageSellOfferOperation`, `ManageBuyOfferOperation`, `XdrLedgerKey.forOffer()`, and `SubmitTransactionResponse.getOfferIdFromResult()` need no type change. The two operations refuse offer id text that is not plain decimal: `"+16"`, `"016"`, and `"0x10"`, which gave id 16 in 3.12.0, throw a `FormatException` from `toXdr()`. Write the id as `"16"`.

  ```dart
  // 3.12.0
  List<BigInt> crossedOfferIds(XdrManageOfferSuccessResult result) => [
    for (final atom in result.offersClaimed)
      if (atom.orderBook != null) atom.orderBook!.offerID.uint64,
  ];
  ```

  ```dart
  // 3.13.0
  List<BigInt> crossedOfferIds(XdrManageOfferSuccessResult result) => [
    for (final atom in result.offersClaimed)
      if (atom.orderBook != null) atom.orderBook!.offerID.int64,
  ];
  ```

## SEP-7 callback URLs

- If your app passes SEP-7 URIs to `URIScheme.signAndSubmitTransaction()` and a `url:` callback is neither `https` with a host nor `http` to `localhost`, `127.0.0.1`, or `[::1]` without userinfo: in 3.13.0 the method throws an `ArgumentError` and sends nothing, for example `Callback URL "http://192.168.1.20:8080/callback" must use https, or http for localhost, 127.0.0.1, or [::1] without userinfo`. A URL that does not parse throws the same error. `on Exception catch` does not catch this `ArgumentError`. In 3.12.0 the method accepted every callback URL that parsed, and a URL that did not parse threw a `FormatException`. A wallet reports the refused callback to its user; a service that issues SEP-7 URIs uses an `https` callback URL with a host.
